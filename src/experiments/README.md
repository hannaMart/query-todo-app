# PB1 — Pobieranie

## 1. Исследовательский вопрос

**Как базовый способ получения server-state в React-приложении влияет на количество HTTP-запросов при первоначальной загрузке данных и при одновременном использовании одного серверного ресурса несколькими независимыми компонентами?**

Сравниваются два подхода:

- **Manual** — `useEffect`, `useState` и `fetch`;
- **React Query** — `useQuery`, `queryKey` и общий механизм управления query.

---

## 2. Цель

Цель PB1 — определить, возникает ли различие в количестве HTTP-запросов между базовой ручной реализацией и React Query:

1. при первоначальном получении server-state одним компонентом;
2. при увеличении количества независимых компонентов, которым одновременно необходим один и тот же server-state.

Основная измеряемая характеристика:

**количество фактически выполненных HTTP-запросов к одному серверному ресурсу.**

PB1 представляет базовую точку сравнения двух подходов.

Дополнительные механизмы ручной координации, кэширования и управления актуальностью данных здесь не используются.

---

## 3. Место PB1 в исследовании

PB1 исследует наиболее базовый аспект работы с server-state — его первоначальное получение.

Последующие исследовательские вопросы расширяют исследование:

- **PB1 — Pobieranie** — получение данных и дублирование одинаковых запросов;
- **PB2 — Synchronizacja** — ошибки, race conditions и асинхронное поведение;
- **PB3 — Aktualność** — актуальность server-state во времени;
- **PB4 — Mutacje** — изменение server-state и последующая синхронизация;
- **PB5 — Parametry** — server-state при изменении параметров запроса;
- **PB6 — Koordynacja** — совместное использование одного server-state несколькими компонентами.

PB1 не исследует способы ручной организации общего состояния между компонентами. Этот аспект отдельно рассматривается в PB6.

---

## 4. Структура PB1

PB1 состоит из двух частей:

### Baseline

Один компонент получает server-state.

Проверяется базовое количество HTTP-запросов при первоначальной загрузке данных.

### Scaling

Десять независимых компонентов одновременно получают один и тот же server-state.

Проверяется, как изменение числа потребителей одного ресурса влияет на количество HTTP-запросов.

Последовательность исследования:

**один компонент → десять независимых компонентов.**

---

## 5. Структура файлов

В обоих проектах используется одинаковая структура:

```text
exp1-pobieranie/

└── scaling.jsx
```

`index-exp1.jsx` содержит навигацию между двумя частями эксперимента.

---

## 6. Источник данных

В PB1 используется публичный REST API:

```text
https://jsonplaceholder.typicode.com/todos
```

Обе реализации обращаются к одному endpoint:

```text
/todos
```

В отличие от последующих экспериментов с `fakeServer`, в PB1 используется реальный HTTP-запрос.

Это необходимо, поскольку основной метрикой PB1 является количество сетевых обращений, непосредственно наблюдаемых в Chrome DevTools.

Содержание отдельных задач не является предметом исследования.

---

## 7. Условия проведения

Оба проекта используют:

- одинаковый endpoint;
- одинаковый набор данных;
- одинаковое количество компонентов;
- одинаковый сценарий запуска;
- одинаковые условия измерения.

`React.StrictMode` отключён.

Это позволяет исключить дополнительные вызовы эффектов development-режима и сравнивать непосредственно поведение исследуемых способов получения server-state.

### Измерение запросов

Используется:

**Chrome DevTools → Network**

Перед каждым измерением:

1. открывается нужная страница эксперимента;
2. открывается вкладка `Network`;
3. включается `Disable cache`;
4. в фильтре указывается `todos`;
5. журнал запросов очищается;
6. выполняется `Reload`;
7. после завершения загрузки подсчитываются запросы к `/todos`.

HTTP-кэш браузера отключается, чтобы его влияние не изменяло результат эксперимента.

# 8. Baseline — первоначальное получение данных

## 8.1. Сценарий

Монтируется один компонент.

Компоненту необходим server-state `/todos`.

После загрузки страницы фиксируется количество HTTP-запросов.

---

## 8.2. Manual

В ручной реализации используется последовательность:

```text
mount компонента
→ useEffect
→ fetch
→ получение данных
→ useState
```

Компонент самостоятельно отвечает за загрузку данных.

Упрощённая логика:

```jsx
useEffect(() => {
  fetch(TODOS_URL)
    .then((response) => response.json())
    .then(setTodos);
}, []);
```

### Результат

Зафиксирован:

**1 HTTP-запрос.**

---

## 8.3. React Query

В реализации React Query используется `useQuery`.

Упрощённая логика:

```jsx
useQuery({
  queryKey: ["exp1", "baseline", "todos"],
  queryFn: fetchTodos,
});
```

Server-state идентифицируется с помощью `queryKey`.

### Результат

Зафиксирован:

**1 HTTP-запрос.**

---

## 8.4. Результаты Baseline

| Подход      | Компоненты | HTTP-запросы |
| ----------- | ---------: | -----------: |
| Manual      |          1 |            1 |
| React Query |          1 |            1 |

---

## 8.5. Вывод Baseline

При первоначальном получении server-state одним компонентом различий в количестве HTTP-запросов между исследуемыми подходами не обнаружено.

И Manual, и React Query выполнили один запрос к `/todos`.

Следовательно, само использование React Query не уменьшает количество запросов в простейшем сценарии первоначальной загрузки.

Baseline используется как контрольная точка для следующего эксперимента.

---

# 9. Scaling — увеличение количества компонентов

## 9.1. Сценарий

На странице одновременно монтируются десять независимых компонентов.

Каждому из них необходим один и тот же ресурс:

```text
/todos
```

Все компоненты появляются одновременно.

Фиксируется общее количество HTTP-запросов.

---

## 9.2. Manual

Каждый компонент самостоятельно содержит:

- собственный `useState`;
- собственный `useEffect`;
- собственный вызов `fetch`.

Компоненты не используют общий cache или общее состояние.

Логика:

```text
Component 1 → fetch /todos
Component 2 → fetch /todos
Component 3 → fetch /todos
...
Component 10 → fetch /todos
```

Каждый компонент независимо инициирует сетевое обращение.

### Результат

**10 компонентов → 10 HTTP-запросов.**

---

## 9.3. React Query

Каждый из десяти компонентов самостоятельно вызывает `useQuery`.

Все компоненты используют одинаковый `queryKey`:

```jsx
queryKey: ["exp1", "scaling", "todos"];
```

Таким образом, все обращения идентифицируются React Query как запрос одного и того же server-state.

При одновременном выполнении одинакового query React Query совместно использует выполняющийся запрос вместо запуска независимого запроса для каждого компонента.

Схема:

```text
Component 1 ─┐
Component 2 ─┤
Component 3 ─┤
...          ├→ один query → один HTTP-запрос
Component 10 ┘
```

### Результат

**10 компонентов → 1 HTTP-запрос.**

---

## 9.4. Результаты Scaling

| Подход      | Компоненты | HTTP-запросы |
| ----------- | ---------: | -----------: |
| Manual      |         10 |           10 |
| React Query |         10 |            1 |

---

## 9.5. Вывод Scaling

При увеличении количества независимых компонентов между подходами появилось существенное различие.

В базовой Manual-реализации каждый компонент самостоятельно инициировал получение server-state.

Поэтому количество HTTP-запросов соответствовало количеству компонентов:

**10 компонентов → 10 запросов.**

В React Query все десять компонентов использовали одинаковый `queryKey`.

При одновременном обращении к одному server-state был выполнен один HTTP-запрос, результат которого использовался несколькими компонентами:

**10 компонентов → 1 запрос.**

Таким образом, различие проявилось не при первоначальном получении данных одним компонентом, а при увеличении количества независимых потребителей одного server-state.

| Scaling — 10 компонентов |     10 |           1 |

# 11. Ответ на исследовательский вопрос

Эксперимент показывает, что влияние выбранного способа управления server-state на количество HTTP-запросов зависит от количества независимых потребителей одного ресурса.

При использовании одного компонента оба подхода показали одинаковое сетевое поведение:

**1 компонент → 1 HTTP-запрос.**

Различие появилось при масштабировании интерфейса.

В базовой Manual-реализации каждый компонент самостоятельно выполняет `fetch`, поэтому десять компонентов инициировали десять одинаковых запросов.

React Query использует `queryKey` для идентификации server-state и способен совместно использовать один выполняющийся query несколькими компонентами.

В результате десять компонентов выполнили один HTTP-запрос.

Следовательно, в исследованном сценарии React Query ограничивает дублирование одновременных запросов к одному server-state, тогда как базовая независимая реализация на основе `useEffect` и `useState` такой координации не содержит.

---

# 12. Границы исследования

PB1 намеренно рассматривает только первоначальное получение server-state.

В нём не исследуются:

- ошибки запросов;
- retry;
- race conditions;
- background refetch;
- `staleTime`;
- актуальность данных во времени;
- повторный mount после длительного перерыва;
- мутации;
- синхронизация после POST/DELETE;
- параметры запроса;
- ручной cache;
- Context API;
- распространение изменений между компонентами.

Эти аспекты исследуются отдельно в PB2–PB6.

---

## 12.1. Граница с PB3

PB1 не исследует вопрос актуальности уже полученных данных.

Влияние времени, `staleTime`, возврата к представлению и повторного получения данных относится к PB3 — Aktualność.

---

## 12.2. Граница с PB6

PB1 Scaling и PB6 используют несколько компонентов, однако предмет исследования различается.

В PB1 Manual-компоненты являются намеренно независимыми:

```text
компонент → собственный useEffect → собственный fetch
```

Цель — определить, как такое базовое устройство влияет на количество запросов.

В PB6 исследуется уже **целенаправленная координация** server-state между компонентами.

Там Manual реализуется с использованием общего состояния через Props или Context API, а React Query — через общий cache.

Следовательно:

**PB1 исследует возникновение дублирования при независимой загрузке.**

**PB6 исследует способы организации общего server-state.**

---

# 13. Ограничения

Manual в PB1 представляет базовую реализацию:

```text
useEffect + useState + fetch
```

Результат:

```text
10 компонентов → 10 запросов
```

не означает, что ручной подход принципиально не способен избежать дублирования.

Разработчик может самостоятельно реализовать:

- общий родительский state;
- Context API;
- custom hook;
- общий cache;
- дедупликацию запросов.

Однако такие механизмы являются дополнительной архитектурой и не входят в базовую реализацию PB1.

Возможность ручной организации общего состояния отдельно проверяется в PB6.

# 15. Итог PB1

PB1 устанавливает базовую точку сравнения двух способов получения server-state.

При одном компоненте различий в количестве HTTP-запросов не обнаружено.

При увеличении числа независимых потребителей одного server-state различие стало существенным:

```text
Manual:
1 компонент  → 1 запрос
10 компонентов → 10 запросов

React Query:
1 компонент  → 1 запрос
10 компонентов → 1 запрос
```

Таким образом, PB1 показывает, что преимущество общего механизма управления query проявляется не обязательно при простейшей первоначальной загрузке, а при появлении нескольких независимых потребителей одинакового server-state.

Эксперимент также создаёт основу для дальнейшего исследования более сложных аспектов управления server-state в PB2–PB6.
