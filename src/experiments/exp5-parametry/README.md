# PB5 — Изменение параметров запроса

## 1. Цель эксперимента

Исследовать, как способ управления server-state влияет на получение, хранение и повторное использование серверных данных при изменении параметров запроса.

Эксперимент направлен на сравнение ручного управления server-state в React и использования библиотеки TanStack Query.

Основной исследовательский вопрос:

**Как способ управления server-state влияет на поведение приложения при изменении параметров запроса?**

В рамках PB5 рассматриваются два аспекта:

1. Получение соответствующего набора серверных данных при изменении параметра запроса.
2. Хранение и повторное использование ранее полученных данных при возвращении к уже использованному параметру.

Для сравнения используются три реализации:

- базовый Manual — без кэширования;
- улучшенный Manual — с самостоятельно реализованным кэшем;
- TanStack Query — со встроенным механизмом кэширования по queryKey.

---

## 2. Место PB5 в общей структуре исследования

PB5 исследует отдельный аспект управления server-state — зависимость идентичности запрашиваемых данных от параметров запроса.

В предыдущих экспериментах рассматривались:

- PB1 — базовое получение серверных данных;
- PB2 — асинхронные ошибки и race condition;
- PB3 — актуальность данных во времени;
- PB4 — мутации и последующая синхронизация.

PB5 исследует ситуацию, когда один серверный ресурс возвращает разные наборы данных в зависимости от параметра запроса.

Например, ресурс todos может возвращать:

- all — все задачи;
- active — только незавершённые задачи;
- completed — только завершённые задачи.

Таким образом, один серверный ресурс представлен несколькими параметризованными наборами данных.

В Manual разработчик самостоятельно определяет зависимость получаемых данных от выбранного параметра и при необходимости организует их хранение.

В TanStack Query параметр включается в queryKey, что позволяет идентифицировать и кэшировать соответствующие данные отдельно.

### Разграничение с другими экспериментами

**PB2 — Race condition**

Исследует конкуренцию асинхронных запросов и предотвращение записи устаревших ответов.

В PB5 не воспроизводится отдельный сценарий быстрой смены параметров с искусственным изменением порядка ответов.

**PB3 — Актуальность данных**

Исследует, когда серверные данные считаются устаревшими и требуется ли повторное получение.

В PB5 актуальность данных во времени не является исследуемой переменной. Проверяется наличие ранее полученных данных для конкретного параметра и возможность их повторного использования.

**PB4 — Мутации**

Исследует изменение серверных данных и последующую синхронизацию состояния приложения.

В PB5 серверные данные не изменяются.

**PB6 — Координация между компонентами**

Исследует совместное использование server-state несколькими компонентами.

В PB5 используется один компонент, который последовательно переключается между параметрами запроса.

## 3. Методология сравнения

Первоначально предполагалось сравнение базового Manual, основанного на useEffect и useState, с TanStack Query.

Однако отсутствие кэширования в базовой ручной реализации само по себе не означает, что ручное управление server-state не позволяет повторно использовать данные.

Поэтому дополнительно рассматривается улучшенный Manual с самостоятельно реализованным кэшем.

Такое сравнение позволяет определить:

- как оба подхода обеспечивают получение данных для разных параметров;
- как наличие кэша влияет на количество обращений к серверу;
- может ли ручная реализация обеспечить аналогичное повторное использование данных;
- какие дополнительные механизмы необходимы для реализации этого поведения вручную.

Задача эксперимента не заключается в определении единственного оптимального способа ручного кэширования.

Ручной кэш рассматривается как один из возможных механизмов, непосредственно влияющих на исследуемую метрику — количество обращений к серверу при повторном выборе параметра.

## 4. Экспериментальная среда

Исследование проводится в двух отдельных React-проектах:

- Manual — ручное управление server-state;
- Query — использование TanStack Query.

В каждом проекте используется одинаковая серверная инфраструктура:

```text
src/
├── fakeServer/
│   ├── db.js
│   └── fakeAPI.js
└── experiments/
    └── exp5-parametry/
```

### 4.1. Источник данных

В общем db.js используется коллекция TODOS:

```js
export const TODOS = [
  { id: 1, title: "Drink 2 litres of water", completed: false },
  { id: 2, title: "Task 2", completed: true },
  { id: 3, title: "Task 3", completed: false },
  { id: 4, title: "Task 4", completed: true },
];
```

Коллекция содержит четыре задачи:

- две активные;
- две завершённые.

PB5 использует существующий набор TODOS. Отдельная изменяемая коллекция для этого эксперимента не требуется, поскольку операции изменения данных отсутствуют.

### 4.2. Серверная функция

В общем fakeServer/fakeAPI.js используется функция:

```js
fakeFetchPb5Todos(filter, delay);
```

Она выполняет:

1. Регистрацию нового обращения через requestId.
2. Имитацию задержки ответа.
3. Фильтрацию серверных данных по выбранному параметру.
4. Возврат соответствующего набора задач.

Структура ответа:

```js
{
  (requestId, items, total);
}
```

Для всех реализаций используется одинаковая задержка:

```js
fakeFetchPb5Todos(filter, 700);
```

Таким образом, имитируется получение ответа через 700 мс.

Каждое новое обращение регистрируется в консоли:

```text
[PB5] request #... START | filter=...
[PB5] request #... END | filter=...
```

Важно: поскольку используется fake API, фиксируются обращения к имитированному серверу, а не реальные HTTP-запросы.

### 4.3. Общие условия

Для всех реализаций используются:

- одинаковые исходные серверные данные;
- одинаковые параметры all, active, completed;
- одинаковая задержка ответа 700 мс;
- одинаковая последовательность пользовательских действий;
- отсутствие мутаций серверных данных.

Перед следующим переключением пользователь дожидается завершения текущего запроса.

Это исключает необходимость повторного исследования конкурирующих асинхронных ответов из PB2.

## 5. Структура эксперимента

PB5 реализован как один эксперимент с тремя вариантами управления server-state.

Для всех вариантов используется одинаковый сценарий:

```text
all → active → completed → all
```

Сценарий состоит из двух последовательных этапов.

### Этап 1 — Первичное получение данных

```text
all → active → completed
```

Исследуется получение серверных данных, соответствующих новому значению параметра.

### Этап 2 — Повторное использование данных

```text
completed → all
```

Исследуется поведение приложения при возвращении к параметру, для которого данные уже были получены.

Проверяется необходимость повторного обращения к серверу.

Оба этапа выполняются в рамках одного экспериментального сценария, а не представляют собой отдельные независимые подэксперименты.

## 6. Реализация Manual

### 6.1. Базовый Manual — param-change.jsx

Используются:

```js
useEffect;
useState;
```

Текущий параметр хранится в состоянии:

```js
const [filter, setFilter] = useState("all");
```

Получение данных организовано через useEffect, зависящий от значения filter:

```js
useEffect(() => {
  // Получение данных для текущего filter
}, [filter]);
```

При изменении filter запускается новое обращение к fake API.

Полученный результат записывается в состояние компонента.

Базовая реализация не содержит кэша по параметрам.

Поэтому при возвращении к ранее выбранному значению all выполняется новое обращение к серверу.

В текущей реализации также предусмотрена защита от записи ответа неактуального эффекта через ignore. Этот механизм не является предметом PB5 и отдельно исследовался в PB2.

### 6.2. Улучшенный Manual — param-cache.jsx

В улучшенной реализации добавлено самостоятельное хранение ранее полученных данных.

Используются:

```js
const [filter, setFilter] = useState("all");
const [data, setData] = useState(null);
const [cache, setCache] = useState({});
```

Кэш представляет собой объект, в котором данные сохраняются по значению параметра:

```js
cache[filter];
```

При первом выборе параметра выполняется обращение к fake API.

После получения ответа результат записывается в кэш:

```js
setCache((prev) => ({
  ...prev,
  [filter]: result,
}));
```

При повторном выборе параметра компонент проверяет наличие сохранённых данных:

```js
if (cache[filter]) {
  setData(cache[filter]);
  setLoading(false);
  return;
}
```

Если данные уже сохранены, они используются повторно без нового обращения к серверу.

Таким образом, улучшенный Manual обеспечивает хранение нескольких параметризованных наборов данных.

В рамках данного эксперимента ручной кэш не имеет ограничения срока актуальности.

Его содержимое сохраняется в состоянии компонента до размонтирования соответствующей реализации.

## 7. Реализация TanStack Query

Используется один компонент:

```text
param-cache.jsx
```

В нём реализованы оба этапа исследовательского сценария.

Получение данных организовано с использованием useQuery:

```js
const { data, isLoading, isFetching } = useQuery({
  queryKey: ["pb5", "todos", filter],
  queryFn: () => fakeFetchPb5Todos(filter, 700),
  staleTime: Infinity,
});
```

### 7.1. Идентификация параметризованных данных

Параметр filter включён в queryKey.

Для разных значений формируются отдельные ключи:

```js
["pb5", "todos", "all"][("pb5", "todos", "active")][
  ("pb5", "todos", "completed")
];
```

Это позволяет TanStack Query различать наборы данных, полученные для разных параметров одного серверного ресурса.

Префикс pb5 используется для изоляции записей кэша этого эксперимента от других экспериментов проекта.

### 7.2. Получение данных

При первом выборе параметра, для которого в кэше отсутствуют данные, выполняется обращение к fake API.

Полученный результат сохраняется в кэше под соответствующим queryKey.

### 7.3. Повторное использование данных

При возвращении к ранее выбранному параметру TanStack Query обращается к записи кэша, соответствующей его queryKey.

Если данные сохранены и считаются актуальными, они используются повторно без выполнения нового запроса.

Для данного эксперимента установлено:

```js
staleTime: Infinity;
```

Это исключает устаревание данных по истечении фиксированного интервала и позволяет сосредоточить исследование на повторном использовании данных по параметру.

При этом staleTime не определяет срок хранения неактивных записей кэша.

В TanStack Query их удаление отдельно регулируется механизмом gcTime.

Поэтому эксперимент проводится в пределах времени хранения неактивных записей.

## 8. Наблюдения и результаты

### 8.1. Этап первичного получения данных

Последовательность:

```text
all → active → completed
```

Для каждого впервые выбранного параметра выполняется получение соответствующих серверных данных.

| Параметр  | Количество задач |
| --------- | ---------------- |
| all       | 4                |
| active    | 2                |
| completed | 2                |

При первоначально пустом кэше для трёх разных параметров выполняются три обращения к fake API.

Обе технологии позволяют получить и отобразить соответствующий набор данных.

Различие заключается в механизме управления состоянием запроса:

- Manual самостоятельно отслеживает изменение параметра и записывает результат в состояние компонента.
- TanStack Query идентифицирует состояние запроса с помощью queryKey.

### 8.2. Этап повторного использования данных

После получения данных для всех трёх параметров пользователь возвращается к all.

В базовом Manual новый выбор all повторно запускает useEffect и инициирует обращение к fake API.

В улучшенном Manual ранее полученные данные all извлекаются из самостоятельно реализованного кэша.

В TanStack Query используются данные, сохранённые под соответствующим queryKey.

При повторном использовании кэшированного результата отображается исходный requestId.

Возвращение прежнего номера запроса не означает выполнение нового обращения к серверу. Это означает, что компонент снова использует результат первоначального запроса.

### 8.3. Количество обращений к fake API

Для контролируемого сценария с первоначально пустым кэшем:

| Реализация        | Первые три параметра | Возврат к all  | Всего |
| ----------------- | -------------------- | -------------- | ----- |
| Базовый Manual    | 3                    | 1 новый запрос | 4     |
| Улучшенный Manual | 3                    | Данные из кэша | 3     |
| TanStack Query    | 3                    | Данные из кэша | 3     |

Проверка показала, что при повторном выборе all базовый Manual инициирует новый запрос, тогда как улучшенный Manual и Query повторно используют сохранённые данные.

Количество обращений определяется по записям START в консоли.

Каждое обращение фиксируется один раз независимо от того, сколько сообщений START и END относится к его выполнению.

| Критерий                                        | Базовый Manual                  | Улучшенный Manual               | TanStack Query    |

| Хранение данных разных параметров               | Не реализовано                  | Ручной кэш                      | Встроенный кэш    |

| Новый запрос при возвращении к all              | Да                              | Нет                             | Нет               |
| Количество обращений в контролируемом сценарии  | 4                               | 3                               | 3                 |
| Дополнительная реализация кэша разработчиком    | Отсутствует                     | Требуется                       | Не требуется      |

### Количество обращений к серверу

При первом выборе новых параметров все три реализации выполняют одинаковое количество обращений к fake API.

Различие проявляется при возвращении к ранее выбранному параметру.

Базовый Manual повторно получает данные.

Улучшенный Manual и TanStack Query используют сохранённый результат.

Следовательно, сокращение количества запросов в данном сценарии связано с наличием кэша, а не исключительно с применением TanStack Query.

### Организация параметризованных данных

В базовом Manual сохраняется текущее состояние компонента.

В улучшенном Manual разработчик самостоятельно организует хранение данных по значениям параметра.

В TanStack Query разделение данных обеспечивается встроенным механизмом кэширования с использованием queryKey.

### Сложность реализации

Для повторного использования данных в Manual необходимо дополнительно реализовать:

- структуру хранения результатов по параметрам;
- проверку наличия ранее полученных данных;
- запись результатов в кэш;
- использование сохранённых результатов при повторном выборе параметра.

В TanStack Query соответствующие механизмы предоставляются библиотекой.

При этом ручная реализация может обеспечить аналогичное поведение в пределах исследуемого сценария.

## 10. Итоговый вывод

Эксперимент PB5 показал, что изменение параметров запроса представляет собой отдельный аспект управления server-state.

Один серверный ресурс может возвращать несколько наборов данных, идентичность которых определяется значениями параметров запроса.

Базовый Manual позволяет корректно получать данные для разных параметров, однако без дополнительного механизма хранения повторный выбор ранее использованного параметра приводит к новому обращению к серверу.

Улучшенный Manual решает эту задачу посредством самостоятельно реализованного кэша по параметрам.

TanStack Query обеспечивает аналогичное повторное использование данных с помощью встроенного механизма кэширования на основе queryKey.

В контролируемом сценарии улучшенный Manual и TanStack Query выполняют одинаковое количество обращений к fake API — три вместо четырёх в базовом Manual.

Таким образом, эксперимент демонстрирует, что ручное управление server-state может обеспечить повторное использование параметризованных данных, но для этого требуется дополнительная реализация соответствующего механизма.

Применение TanStack Query позволяет использовать уже предусмотренные библиотекой средства идентификации и кэширования данных по параметрам запроса.

Полученные результаты относятся к исследованным условиям и не означают, что TanStack Query всегда выполняет меньше запросов или что ручной подход не способен обеспечить сопоставимое поведение.

## 11. Ограничения эксперимента

Исследование проводится в контролируемой среде с имитированным серверным API.

Используются неизменяемые серверные данные и одинаковая искусственная задержка ответа.

В рамках PB5 не исследуются:

- конкурентное выполнение запросов с изменением порядка ответов;
- повторное использование незавершённых запросов;
- изменение актуальности данных со временем;
- автоматическая инвалидация кэша после мутаций;
- координация одного server-state между несколькими компонентами.

Эти аспекты либо рассматриваются в других экспериментальных вопросах, либо находятся за пределами выбранного сценария PB5.

Для сравнения количества запросов каждый вариант запускается с первоначально пустым соответствующим кэшем.

В режиме разработки React StrictMode может влиять на количество вызовов эффектов при монтировании компонента. Поэтому при фиксации результатов необходимо учитывать конфигурацию среды выполнения.

Результаты сравнения относятся к выбранным условиям и не распространяются автоматически на все возможные реализации ручного управления server-state или конфигурации TanStack Query.
