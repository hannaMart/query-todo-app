Эксперимент 5 — Изменение параметров запроса
Цель эксперимента

Определить, как выбранный способ управления server-state (ручной подход с использованием useEffect и useState по сравнению с библиотекой TanStack Query) влияет на поведение приложения при изменении параметров запроса, в частности на количество HTTP-запросов, повторное использование данных и согласованность отображаемых результатов.

🔹 Метод эксперимента

В рамках эксперимента сравниваются два подхода:

ручная реализация (useEffect + useState),
реализация с использованием TanStack Query.

Во всех подпунктах используются одинаковые условия:

единый источник данных (fakeFetch),
одинаковый интерфейс (список + фильтр),
одинаковые параметры (all, active, completed),
искусственная задержка ответа,
логирование запросов (requestId).
🔹 5a. Изменение параметров запроса
Сценарий

Пользователь:

открывает страницу,
изменяет фильтр (например, all → active → completed).
Анализ
Ручная реализация
при каждом изменении параметра выполняется новый HTTP-запрос,
управление состоянием полностью реализуется вручную,
отображаемые данные напрямую зависят от текущего состояния компонента.
TanStack Query
изменение параметра приводит к изменению queryKey,
для каждого параметра формируется отдельный запрос,
возможна автоматическая подстановка данных из кэша.
Вывод

Обе реализации корректно обновляют данные при смене параметра.
Однако TanStack Query обеспечивает более структурированное управление запросами и позволяет использовать кэш без дополнительной логики.

🔹 5b. Быстрая последовательная смена параметров
Сценарий

Пользователь быстро изменяет параметры:

all → active → completed

С минимальными интервалами времени.

Анализ
Ручная реализация
инициируется несколько запросов подряд,
ответы могут приходить в произвольном порядке,
требуется дополнительная логика (например, ignore) для предотвращения записи устаревших данных,
без защиты возможно отображение некорректного результата.
TanStack Query
каждый параметр связан с отдельным queryKey,
ответы автоматически сопоставляются с соответствующим состоянием,
отсутствует необходимость ручной защиты от race condition,
поведение более предсказуемо.
Вывод

TanStack Query снижает сложность обработки быстрых изменений параметров и уменьшает риск отображения устаревших данных по сравнению с ручной реализацией.

🔹 5c. Использование кэша
Сценарий

Пользователь:

all → active → completed → снова all
Анализ
Ручная реализация
для повторного использования данных требуется ручная реализация кэша,
данные сохраняются в объекте по ключу параметра,
при возврате к параметру данные могут быть взяты из кэша без нового запроса.
TanStack Query
кэш встроен в библиотеку,
данные автоматически сохраняются по queryKey,
при наличии актуальных данных новый запрос не выполняется,
параметр staleTime управляет актуальностью данных.
Вывод

TanStack Query обеспечивает автоматическое кэширование без необходимости ручной реализации, что упрощает код и снижает количество повторных запросов.

Количество HTTP-запросов

TanStack Query:

Поведение интерфейса
manual:
возможны мигание, сброс данных и менее предсказуемое поведение без дополнительной обработки.
TanStack Query:
интерфейс обновляется более плавно, возможна работа с предыдущими данными во время загрузки.

загрузкой,

TanStack Query:
большая часть логики реализована внутри библиотеки.

Использование TanStack Query позволяет автоматизировать обработку параметров запроса, снизить количество повторных HTTP-запросов и обеспечить более предсказуемое и согласованное поведение приложения.

🔹 1. «А это не повтор экспериментов про синхронизацию?»

Ответ:

Нет. В предыдущих экспериментах анализировалась синхронизация во времени и поведение асинхронных запросов. Здесь исследуется изменение параметров запроса, то есть переход между разными наборами данных. Это отдельный аспект управления server-state.

🔹 2. «Почему вы не использовали реальный API?»

Ответ:

Для обеспечения одинаковых условий эксперимента использовался fake API. Это позволило контролировать задержку, порядок ответов и исключить влияние внешних факторов, таких как сеть или сервер.

🔹 3. «А зачем вообще нужен queryKey?»

Ответ:

queryKey определяет уникальность запроса. При изменении параметров меняется ключ, и библиотека понимает, что это другой запрос. Это также позволяет кэшировать данные отдельно для каждого параметра.

🔹 4. «Почему в manual возникают проблемы при быстрых изменениях?»

Ответ:

Потому что несколько запросов выполняются параллельно, и ответы могут приходить в разном порядке. Без дополнительной логики возможно отображение устаревших данных.

🔹 5. «Как TanStack Query решает эту проблему?»

Ответ:

Он связывает данные с конкретным queryKey, поэтому даже если ответы приходят в разном порядке, они не перезаписывают состояние для другого параметра.

🔹 6. «Можно ли сделать manual так же хорошо?»

Ответ:

Да, но потребуется реализовать кэш, контроль актуальности данных и защиту от race condition вручную, что увеличивает сложность кода.

🔹 7. «А кэш в TanStack Query всегда используется?»

Ответ:

Нет. Использование кэша зависит от параметров, таких как staleTime. Если данные считаются устаревшими, выполняется новый запрос.

🔹 8. «Почему в 5c вы используете staleTime?»

Ответ:

Чтобы продемонстрировать повторное использование данных. Без staleTime библиотека может сразу выполнять повторный запрос, и эффект кэша будет менее заметен.

🔹 9. «Чем отличается кэш в manual и в query?»

Ответ:

В manual кэш реализуется вручную, обычно через объект. В TanStack Query кэш встроен и автоматически управляется на основе queryKey.

🔹 10. «Где в вашем эксперименте видно уменьшение количества запросов?»

Ответ:

В подпункте 5c при возврате к ранее использованному параметру. В TanStack Query данные могут быть взяты из кэша без нового запроса, тогда как в manual это требует дополнительной реализации.

🔹 11. «А если пользователь долго не возвращается?»

Ответ:

Тогда данные могут считаться устаревшими, и TanStack Query выполнит новый запрос в зависимости от настроек, например staleTime.

🔹 12. «Что является главным выводом эксперимента?»

Ответ:

TanStack Query упрощает управление server-state при изменении параметров запроса, снижает количество повторных запросов и обеспечивает более предсказуемое поведение по сравнению с ручной реализацией.

🔹 13. «Что самое важное отличие manual и query?»

Ответ (коротко):

В manual параметр просто триггерит запрос, а в TanStack Query он становится частью queryKey, что автоматически включает кэш и управление состоянием.
