## Общий вывод PB6 — Koordynacja

В шестом эксперименте исследовалось влияние выбранного способа управления server-state на совместное использование серверных данных несколькими компонентами React-приложения.

Исследование включало три сценария:

- PB6a — совместный доступ двух компонентов к одинаковым серверным данным;
- PB6b — формирование разных представлений одного server-state;
- PB6c — распространение изменений серверных данных между компонентами.

В каждом сценарии сравнивались три реализации: Manual — Props, Manual — Context API и React Query.

### Результаты исследования

Во всех трёх сценариях ручные реализации и React Query обеспечили одинаковое количество API-запросов и согласованное отображение серверных данных.

В PB6a и PB6b одного API-запроса было достаточно для получения данных всеми компонентами.

В PB6c после добавления задачи во всех реализациях выполнялась одинаковая последовательность серверных операций: первоначальный GET, POST и повторный GET. Обновлённые данные становились доступны всем компонентам без необходимости выполнять отдельные запросы для каждого из них.

Таким образом, эксперимент подтвердил, что при соответствующей организации ручного управления server-state можно избежать дублирования API-запросов и обеспечить согласованность представлений без использования специализированной библиотеки.

### Различия между подходами

Основные различия проявились в способе организации общего состояния и предоставления данных компонентам.

**Manual — Props:** загрузка, хранение и обновление server-state организуются в родительском компоненте. Данные и функции изменения явно передаются дочерним компонентам через props.

**Manual — Context API:** загрузка, хранение и обновление server-state организуются в Provider. Компоненты получают доступ к общему состоянию и функциям изменения через useContext без необходимости передачи через props. При этом логика работы с серверными данными остаётся реализованной вручную.

**React Query:** общее состояние организуется с использованием QueryClient и кэша. Компоненты самостоятельно обращаются к серверным данным через useQuery с одинаковым queryKey. После мутации обновление общего состояния инициируется через invalidateQueries, а распространение полученных данных обеспечивается механизмами библиотеки.

### Итоговый вывод

**PB6 показал, что различия между ручным управлением server-state и React Query заключаются не обязательно в количестве API-запросов или согласованности конечного состояния, а прежде всего в механизмах организации совместного доступа к данным и распространения изменений между компонентами.**

Ручные реализации требуют явной организации общего состояния, загрузки данных и последующей синхронизации. React Query предоставляет специализированные механизмы общего кэширования, идентификации серверных данных и координации их обновления.

В пределах исследованных сценариев все три подхода обеспечили одинаковое наблюдаемое поведение приложения. Следовательно, результаты PB6 не подтверждают преимущества React Query по количеству API-запросов относительно корректно организованных ручных реализаций.

При этом эксперимент выявил архитектурные различия между подходами, которые необходимо учитывать при интерпретации результатов исследования и формулировании общего вывода магистерской работы.
