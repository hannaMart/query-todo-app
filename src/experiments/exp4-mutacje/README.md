PB4 — Мутации (React Query)
Общая цель блока

Целью блока PB4 является анализ поведения приложения при выполнении операций изменения данных и сравнение подходов к синхронизации server-state после мутаций.

В части, реализованной с использованием React Query, исследуется, каким образом библиотека обеспечивает согласованность интерфейса после операций добавления и удаления данных, а также как это влияет на количество HTTP-запросов и предсказуемость поведения приложения.

В отличие от предыдущего блока, посвящённого чтению данных и контролю их актуальности, в данном эксперименте рассматриваются именно мутации, то есть ситуации, в которых пользователь изменяет данные на стороне сервера, а интерфейс должен корректно отразить это изменение.

4a — Добавление элемента (add)
Цель

Целью подпункта 4a является исследование поведения приложения после добавления нового элемента в систему при использовании React Query.

Основное внимание уделяется следующим аспектам:

корректно ли новый элемент появляется в пользовательском интерфейсе;
происходит ли синхронизация состояния автоматически;
сколько HTTP-запросов выполняется после мутации;
насколько предсказуемо приложение обновляет данные после изменения server-state.
Сценарий эксперимента

В рамках данного сценария пользователь вводит название нового элемента и инициирует операцию добавления.

В реализации React Query используются:

useQuery для получения списка элементов;
useMutation для выполнения операции добавления;
invalidateQueries для последующей синхронизации данных.

Последовательность действий выглядит следующим образом:

При открытии компонента выполняется исходный запрос GET, который загружает текущий список элементов.
Пользователь вводит новый элемент.
После нажатия кнопки запускается мутация POST.
После успешного завершения мутации вызывается invalidateQueries.
React Query автоматически помечает кэшированные данные как требующие обновления и инициирует повторный запрос GET.
После завершения повторного запроса интерфейс отображает уже обновлённый список.

Таким образом, в данном сценарии используется модель:

GET → POST → invalidate → GET

или, если считать только действия после мутации:

POST → GET

Метрики

В подпункте 4a оцениваются следующие метрики:

количество HTTP-запросов после мутации;
корректность данных в UI;
способ синхронизации;
предсказуемость поведения;
сложность реализации.
Наблюдения
1. Количество HTTP-запросов

После операции добавления React Query выполняет:

один запрос POST для записи нового элемента;
один дополнительный GET для повторного получения актуального списка.

Следовательно, после мутации возникает два сетевых действия: запись и последующее обновление данных.

Это означает, что по сравнению с ручным вариантом, в котором интерфейс можно обновить только через setState без дополнительного запроса, React Query в типовом сценарии генерирует больший сетевой трафик.

2. Корректность данных в UI

После выполнения мутации и повторного запроса новый элемент появляется в интерфейсе корректно.

Поскольку данные после добавления не конструируются вручную в локальном состоянии, а повторно получаются из общего источника данных, интерфейс оказывается согласован с серверным состоянием.

Именно это является одним из ключевых преимуществ данного подхода: после мутации React Query не полагается исключительно на локальное предположение о результате, а инициирует повторную синхронизацию.

3. Способ синхронизации

Синхронизация в React Query в данном сценарии происходит автоматически после явно заданной инструкции invalidateQueries.

Это важно сформулировать точно.

Здесь не происходит «магического» самопроизвольного обновления без участия разработчика. Разработчик всё же должен указать, что после успешной мутации соответствующие данные необходимо инвалидировать. Однако после этого вся дальнейшая логика повторного получения данных уже выполняется библиотекой автоматически.

Следовательно, можно сказать, что:

решение о необходимости обновления задаётся разработчиком;
сама процедура повторной синхронизации реализуется React Query автоматически.
4. Предсказуемость поведения

Поведение приложения после мутации является предсказуемым.

Если мутация завершилась успешно и был вызван invalidateQueries, React Query повторно запрашивает данные и обновляет интерфейс. Это делает сценарий стабильным и легко интерпретируемым: после изменения данных список будет приведён к актуальному состоянию.

В данном случае предсказуемость выше, чем в ручном варианте с локальным setState, поскольку корректность результата не зависит от того, насколько аккуратно программист вручную обновил массив в состоянии.

5. Сложность реализации

С точки зрения кода реализация остаётся достаточно компактной:

не требуется вручную вызывать отдельную функцию загрузки списка;
не требуется вручную формировать новый массив элементов после мутации;
библиотека берёт на себя повторное получение данных и обновление состояния интерфейса.

При этом следует отметить, что такая простота достигается ценой использования механизмов React Query и дополнительного refetch.

Вывод по 4a

Эксперимент 4a показывает, что в React Query добавление элемента сопровождается автоматизированной синхронизацией данных через механизм invalidateQueries.

Это обеспечивает:

корректное появление нового элемента в UI;
высокую согласованность между интерфейсом и серверным состоянием;
предсказуемое поведение после мутации.

Однако данная стратегия сопровождается дополнительным запросом GET, что увеличивает сетевую стоимость операции по сравнению с ручным локальным обновлением через setState.

4b — Удаление элемента (delete)
Цель

Целью подпункта 4b является анализ поведения приложения после удаления элемента при использовании React Query.

Исследование направлено на проверку:

корректно ли удалённый элемент исчезает из пользовательского интерфейса;
не остаются ли в UI устаревшие или «фантомные» данные;
каким образом React Query выполняет синхронизацию после удаления;
сколько HTTP-запросов требуется для поддержания актуального состояния списка.
Сценарий эксперимента

В рамках эксперимента пользователь инициирует удаление одного из элементов списка.

В реализации используются:

useQuery для загрузки исходного списка;
useMutation для выполнения операции удаления;
invalidateQueries для принудительного обновления данных после успешной мутации.

Последовательность действий следующая:

При открытии компонента выполняется GET и отображается исходный список.
Пользователь нажимает кнопку удаления.
Выполняется мутация DELETE.
После успешного завершения удаления вызывается invalidateQueries.
React Query повторно получает список через GET.
Интерфейс отображает уже обновлённые данные без удалённого элемента.

Следовательно, сценарий имеет форму:

GET → DELETE → invalidate → GET

или после мутации:

DELETE → GET

Метрики

В подпункте 4b оцениваются:

количество HTTP-запросов после удаления;
корректность данных в UI;
способ синхронизации;
предсказуемость поведения;
сложность реализации.
Наблюдения
1. Количество HTTP-запросов

После удаления React Query выполняет:

один запрос DELETE;
один дополнительный GET для повторной загрузки списка.

Итог: после мутации снова наблюдаются два действия на сетевом уровне.

Это подтверждает ту же закономерность, что и в случае добавления: типовой сценарий React Query после мутации предполагает автоматическое повторное получение данных.

2. Корректность данных в UI

После повторного запроса удалённый элемент исчезает из интерфейса корректно.

Поскольку список не редактируется вручную локально, а повторно извлекается из источника данных, риск сохранения устаревшего элемента в UI снижается.

Это особенно важно для операций удаления, так как именно здесь хорошо заметен риск появления «фантомных» записей, если интерфейс не был корректно синхронизирован после изменения данных.

В React Query этот риск минимизируется за счёт повторного получения актуального списка.

3. Способ синхронизации

Как и в случае добавления, синхронизация строится по схеме:

успешная мутация;
инвалидирование запроса;
автоматический refetch.

Следовательно, подход остаётся декларативным: разработчик не пишет заново логику загрузки списка и не изменяет вручную массив в state, а задаёт правило, что после мутации данные необходимо обновить.

Это снижает объём ручного кода и делает логику обновления более единообразной.

4. Предсказуемость поведения

Поведение после удаления остаётся предсказуемым.

Если мутация завершилась успешно, React Query автоматически инициирует повторную синхронизацию, и интерфейс приходит в корректное состояние.

С практической точки зрения это означает, что после удаления данные в UI ведут себя ожидаемо и последовательно, без необходимости ручного контроля за структурой списка.

5. Сложность реализации

Реализация удаления в React Query также остаётся компактной.

Не требуется:

вручную фильтровать массив элементов в локальном состоянии;
вручную вызывать функцию повторной загрузки;
явно синхронизировать разные части интерфейса.

Вместо этого используется единый механизм мутации и инвалидирования запроса.

Вывод по 4b

Эксперимент 4b показывает, что React Query обеспечивает корректное удаление элемента из интерфейса за счёт повторной синхронизации данных после мутации.

Подход позволяет:

избежать сохранения устаревших элементов в UI;
поддерживать высокую согласованность интерфейса с серверным состоянием;
обеспечить предсказуемую модель поведения.

Как и в случае добавления, цена этой согласованности — дополнительный запрос GET после мутации.

4c — Сравнительный анализ стратегии синхронизации после мутации
Почему для 4c не создавался отдельный код

Это важный момент, и его лучше сформулировать прямо.

Подпункт 4c не является отдельным техническим сценарием с новым поведением компонента. Он представляет собой аналитическое обобщение результатов, полученных в экспериментах 4a и 4b.

Иными словами:

в 4a уже наблюдается поведение системы после добавления;
в 4b уже наблюдается поведение системы после удаления;
в обоих случаях уже видно, как именно выполняется синхронизация.

Следовательно, отдельный интерактивный компонент для 4c не добавляет нового экспериментального материала. Он лишь искусственно дублировал бы уже реализованную логику.

Поэтому 4c корректно оформляется как аналитический подпункт, а не как самостоятельная реализация.

Это относится и к ручной части, и к части React Query.

Цель 4c

Целью 4c является обобщение результатов предыдущих подпунктов и анализ того, каким образом выбранный подход к управлению server-state влияет на:

характер синхронизации после мутаций;
необходимость ручного вмешательства;
количество дополнительных HTTP-запросов;
предсказуемость поведения приложения.
Основание для анализа

Анализ выполняется на основе результатов:

4a — добавление элемента;
4b — удаление элемента.

Именно эти два эксперимента дают полный материал, необходимый для оценки стратегии синхронизации после мутаций.

Наблюдения по React Query

На основе экспериментов 4a и 4b можно сделать следующие наблюдения.

1. Синхронизация после мутации не требует ручного обновления локального списка

В React Query разработчику не требуется после POST или DELETE вручную:

заново загружать список отдельной функцией;
конструировать новый массив элементов;
самостоятельно фильтровать или дополнять состояние интерфейса.

После мутации достаточно указать, что соответствующий запрос должен быть инвалидирован.

2. Повторное получение данных выполняется автоматически

После вызова invalidateQueries библиотека сама инициирует повторный GET, если соответствующий запрос активен.

Это означает, что React Query предоставляет встроенный механизм реконсиляции данных после мутации.

3. Поведение становится более единообразным

Обе мутации — добавление и удаление — обрабатываются по одной и той же модели:

выполнить мутацию;
инвалидировать кэш;
повторно получить актуальные данные.

Такое единообразие повышает предсказуемость архитектуры и упрощает сопровождение кода.

4. Цена автоматизированной синхронизации — дополнительные запросы

В обоих сценариях после мутации возникает дополнительный GET.

Следовательно, React Query снижает объём ручной логики, но увеличивает сетевую стоимость типовой мутации по сравнению с ручным локальным обновлением состояния.

Такой подход обеспечивает:

согласованность интерфейса с серверным состоянием;
высокую предсказуемость поведения;
уменьшение объёма ручной логики синхронизации.

Вместе с тем он приводит к дополнительным HTTP-запросам после мутации, что делает синхронизацию более дорогой с точки зрения сетевой нагрузки.

PB4 — Сравнительный анализ стратегий синхронизации после мутаций
Цель сравнительного анализа

Целью данного этапа является сопоставление двух подходов к управлению server-state в React-приложении:

императивного (ручного управления состоянием);
декларативного (с использованием библиотеки React Query),

в контексте выполнения операций изменения данных (мутаций).

Анализ проводится на основе результатов подпунктов:

4a — добавление элемента;
4b — удаление элемента.

Основное внимание уделяется:

согласованности пользовательского интерфейса;
способу синхронизации данных;
количеству HTTP-запросов после мутации;
предсказуемости поведения;
сложности реализации.
1. Согласованность пользовательского интерфейса
Ручной подход

В ручной реализации согласованность интерфейса после мутации не обеспечивается автоматически.

После выполнения операций POST или DELETE состояние UI остаётся прежним до тех пор, пока разработчик явно не обновит его одним из способов:

повторный запрос данных (refetch);
локальное обновление состояния (setState).

Таким образом, корректность отображения данных напрямую зависит от реализованной логики.

При использовании refetch согласованность достигается за счёт повторного получения данных с сервера.

При использовании setState согласованность обеспечивается вручную и может быть нарушена при ошибках в реализации.

React Query

В React Query согласованность интерфейса обеспечивается через механизм инвалидирования и автоматического refetch.

После успешной мутации:

данные помечаются как устаревшие;
выполняется повторный запрос;
интерфейс обновляется на основе актуального состояния.

В результате UI синхронизируется с сервером без необходимости ручного обновления массива данных.

Вывод

React Query обеспечивает более стабильную и надёжную согласованность интерфейса, тогда как в ручном подходе она зависит от корректности реализации.

2. Способ синхронизации данных
Ручной подход

Синхронизация полностью контролируется разработчиком.

После мутации необходимо явно выбрать стратегию:

вызвать повторный GET (refetch);
обновить состояние локально (setState).

Отсутствует встроенный механизм автоматического приведения данных к актуальному состоянию.

React Query

Синхронизация реализуется декларативно:

разработчик указывает, что данные необходимо обновить (invalidateQueries);
библиотека автоматически инициирует refetch и обновляет UI.

Таким образом, логика синхронизации централизована и унифицирована.

Ручной подход предоставляет полный контроль над синхронизацией, тогда как React Query автоматизирует этот процесс и снижает необходимость ручного управления состоянием.

3. Количество HTTP-запросов
Ручной подход

Возможны два варианта:

refetch:
POST/DELETE + GET → 2 запроса
setState:
только POST/DELETE → 1 запрос

Таким образом, ручной подход позволяет оптимизировать сетевую нагрузку за счёт отказа от повторного запроса.

React Query

Типовой сценарий:

POST/DELETE + GET (через invalidate) → 2 запроса

Дополнительный GET выполняется автоматически после мутации.

Вывод

Ручной подход может быть более эффективным по количеству запросов, тогда как React Query, как правило, генерирует дополнительный сетевой трафик для обеспечения согласованности данных.

4. Предсказуемость поведения
Ручной подход

Предсказуемость зависит от реализации:

при refetch поведение стабильно;
при setState возможны ошибки синхронизации.

Разные участки кода могут реализовывать обновление данных по-разному, что снижает единообразие поведения приложения.

React Query

Поведение стандартизировано:

после мутации выполняется invalidate;
затем автоматически выполняется refetch;
UI обновляется.

Это делает поведение приложения более единообразным и предсказуемым.

Вывод

React Query обеспечивает более высокий уровень предсказуемости благодаря унифицированной модели синхронизации.

5. Сложность реализации
Ручной подход

Требует:

написания логики загрузки данных;
ручного вызова refetch;
ручного обновления состояния (setState);
контроля за корректностью данных.

Код становится более детализированным и подверженным ошибкам.

React Query

Позволяет:

использовать единый механизм useQuery и useMutation;
делегировать синхронизацию библиотеке;
сократить количество ручного кода.

Однако требует понимания концепций кэширования и инвалидирования.

Вывод

React Query снижает объём ручной логики, но требует освоения дополнительного инструмента.
