# PB4 — Мутации и синхронизация данных (React Query)

## Общая цель

Цель PB4 — исследовать поведение приложения после изменения server-state и сравнить разные стратегии синхронизации пользовательского интерфейса с серверными данными.

В эксперименте рассматриваются две принципиально разные стратегии:

1. **повторное получение server-state после мутации**;
2. **обновление клиентского представления данных без повторного получения списка**.

В React Query этим стратегиям соответствуют:

- `invalidateQueries` → повторное получение данных;
- `setQueryData` → непосредственное обновление query cache.

Эксперимент не ставит целью исследовать все возможные механизмы React Query. Выбраны две стратегии, которые принципиально различаются способом восстановления согласованности данных и имеют прямые аналоги в ручной реализации.

---

# 4a — Добавление элемента

## Цель

Исследовать поведение приложения после добавления нового элемента и сравнить две стратегии синхронизации server-state в React Query.

## Сценарий

Пользователь добавляет новый элемент.

В обоих вариантах:

1. исходный список загружается через `useQuery`;
2. добавление выполняется через `useMutation`;
3. после успешной мутации интерфейс должен отобразить новый элемент.

Различается только способ последующей синхронизации.

---

## Вариант 1 — `invalidateQueries`

Последовательность:

`ADD → invalidateQueries → GET`

После успешного добавления разработчик явно инвалидирует query.

React Query:

- помечает соответствующие данные как устаревшие;
- для активного query выполняет повторное получение данных;
- обновляет query cache;
- вызывает повторный рендер компонентов, использующих эти данные.

### Наблюдения

После мутации выполняются два обращения к API:

- добавление элемента;
- повторное получение списка.

Преимущества:

- интерфейс формируется на основании повторно полученного server-state;
- не требуется вручную добавлять новый элемент в cache;
- одна и та же модель синхронизации может применяться к различным мутациям.

Недостатки:

- требуется дополнительное обращение к API;
- повторно запрашивается весь список, даже если результат мутации уже известен клиенту.

---

## Вариант 2 — `setQueryData`

Последовательность:

`ADD → setQueryData`

После успешной мутации повторное получение списка не выполняется.

Результат операции добавления используется для непосредственного обновления query cache.

### Наблюдения

После мутации выполняется одно обращение к API — добавление элемента.

Новый объект, возвращённый fake API, добавляется непосредственно в существующие данные query cache.

Преимущества:

- отсутствует дополнительное получение списка;
- уменьшается количество обращений к API;
- server-state продолжает храниться в централизованном query cache.

Недостатки:

- разработчик должен явно определить способ изменения cache;
- корректность результата зависит от правильности логики обновления query cache.

---

## Вывод по 4a

Обе стратегии позволяют корректно отобразить новый элемент после мутации, но достигают этого разными способами.

`invalidateQueries` повторно получает server-state из источника данных.

`setQueryData` использует результат мутации для непосредственного изменения клиентского представления server-state в query cache.

Таким образом, различие заключается прежде всего в выборе между повторным получением данных и локальным обновлением cache.

---

# 4b — Удаление элемента

## Цель

Исследовать поведение приложения после удаления элемента и сравнить две стратегии синхронизации server-state в React Query.

## Сценарий

Пользователь удаляет существующий элемент.

В обоих вариантах:

1. исходный список загружается через `useQuery`;
2. удаление выполняется через `useMutation`;
3. после успешной мутации удалённый элемент должен исчезнуть из UI.

---

## Вариант 1 — `invalidateQueries`

Последовательность:

`DELETE → invalidateQueries → GET`

После успешного удаления query инвалидируется.

React Query повторно получает список и обновляет cache актуальными данными.

### Наблюдения

После мутации выполняются:

- операция удаления;
- повторное получение списка.

Удалённый элемент исчезает из UI после получения обновлённых данных.

Преимущества:

- состояние списка повторно формируется на основании server-state;
- не требуется самостоятельно удалять элемент из query cache.

Недостатки:

- выполняется дополнительное обращение к API;
- повторно получается весь список.

---

## Вариант 2 — `setQueryData`

Последовательность:

`DELETE → setQueryData`

После успешного удаления повторное получение списка не выполняется.

На основании идентификатора удалённого элемента соответствующая запись удаляется непосредственно из query cache.

### Наблюдения

После мутации выполняется одно обращение к API — удаление элемента.

Интерфейс обновляется вследствие изменения query cache.

Преимущества:

- отсутствует дополнительное получение списка;
- уменьшается количество обращений к API;
- изменение остаётся централизованным в механизме server-state React Query.

Недостатки:

- разработчик самостоятельно определяет логику изменения cache;
- неправильное обновление query cache может привести к рассинхронизации клиентского представления данных.

---

## Вывод по 4b

Удаление подтверждает ту же закономерность, что и добавление.

`invalidateQueries` восстанавливает согласованность через повторное получение server-state.

`setQueryData` восстанавливает согласованность через непосредственное изменение query cache без дополнительного получения списка.

---

# 4c — Сравнение стратегий синхронизации

## Назначение

4c не является отдельным интерактивным экспериментом.

Он представляет аналитическое сравнение результатов 4a и 4b.

Отдельный сценарий не создаётся, поскольку в нём отсутствовала бы новая исследуемая переменная. Повторная реализация мутации лишь дублировала бы уже наблюдаемое поведение.

Материал для анализа полностью предоставляют:

- 4a — добавление элемента;
- 4b — удаление элемента.

---

## Сравнение стратегий React Query

| Характеристика                        | `invalidateQueries`                   | `setQueryData`                    |
| ------------------------------------- | ------------------------------------- | --------------------------------- |
| Повторное получение списка            | да                                    | нет                               |
| Источник нового состояния             | повторный результат API               | результат мутации + текущий cache |
| Изменение query cache                 | выполняется React Query после refetch | задаётся разработчиком            |
| Дополнительное обращение к API        | да                                    | нет                               |
| Объём ручной логики обновления данных | меньше                                | больше                            |

Обе стратегии являются корректными способами управления server-state в React Query.

Различие заключается не в том, что одна стратегия «правильная», а другая «неправильная», а в компромиссе между:

- повторным получением данных из источника;
- количеством обращений к API;
- объёмом логики, необходимой для обновления клиентского cache.

---

# Сопоставление с ручной реализацией

Для обеспечения сопоставимости экспериментов исследуются одинаковые две модели синхронизации.

| Стратегия                        | Manual     | React Query                   |
| -------------------------------- | ---------- | ----------------------------- |
| Повторное получение server-state | `refetch`  | `invalidateQueries` + refetch |
| Обновление без повторного GET    | `setState` | `setQueryData`                |

При этом `setState` и `setQueryData` не являются технически одинаковыми механизмами.

В Manual данные хранятся и обновляются непосредственно в состоянии компонента.

В React Query server-state хранится в query cache, а `setQueryData` изменяет именно этот централизованный cache.

Сопоставление проводится по выполняемой ими роли в эксперименте: обе стратегии позволяют отразить результат мутации без повторного получения всего списка.

---

# Почему исследуются add и delete

Добавление и удаление выбраны как два противоположных изменения коллекции:

- `add` создаёт новую сущность в server-state;
- `delete` удаляет существующую сущность из server-state.

Оба сценария позволяют проверить, сохраняется ли одна и та же закономерность синхронизации при разных направлениях изменения коллекции.

Отдельный сценарий `update` не включён, поскольку для поставленного исследовательского вопроса он не вводит принципиально новой стратегии синхронизации: после изменения существующего объекта снова применялся бы либо повторный запрос данных, либо непосредственное обновление клиентского представления server-state.

---

# Метрики PB4

В эксперименте оцениваются:

- количество обращений к API после мутации;
- способ восстановления согласованности server-state и UI;
- корректность отображаемых данных;
- объём ручной логики синхронизации;
- предсказуемость поведения;
- различие между локальным состоянием компонента и централизованным query cache.

---

# Итог PB4 — React Query

PB4 показывает, что React Query не навязывает единственный способ синхронизации после мутации.

Разработчик может выбрать между двумя принципиально различными стратегиями:

- инвалидировать данные и повторно получить server-state;
- непосредственно обновить query cache на основании результата мутации.

`invalidateQueries` уменьшает объём логики, необходимой для ручного изменения данных, но приводит к дополнительному обращению к API.

`setQueryData` позволяет избежать повторного получения списка, однако требует от разработчика корректно определить изменение cache.

Таким образом, преимущество React Query заключается не просто в автоматическом выполнении refetch после мутации, а в предоставлении специализированного механизма управления server-state, в котором разные стратегии синхронизации реализуются через единый query cache.

Это позволяет сравнивать React Query с ручным подходом не по наличию или отсутствию конкретного дополнительного запроса, а по способу организации и управления синхронизацией server-state.
