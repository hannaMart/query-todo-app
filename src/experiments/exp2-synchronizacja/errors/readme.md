## Общее описание

Эта часть PB2 исследует поведение server - state при ошибках асинхронных запросов и их повторном выполнении.

Цель — сравнить не идентичность реализации, а то, ** как manual - подход и React Query обрабатывают одинаковые события **:

** запрос → успех или ошибка → повторный запрос(retry).**

В manual - реализации разработчик самостоятельно управляет состояниями `loading`, `error`, `success`, данными и логикой повторного запроса.Поэтому отдельно демонстрируются ошибочная и исправленная реализации.

В React Query состояния запроса управляются библиотекой, поэтому искусственно создавать аналогичную ошибочную реализацию не требуется.Сравнивается штатный способ обработки того же сценария средствами`useQuery`.

Для сохранения сопоставимых условий оба подхода используют один и тот же`fakeAPI`, одинаковые данные и одинаковую задержку ответа.

### Retry

Следует различать два варианта повторного запроса:

- ** ручной retry ** — пользователь инициирует повторный запрос кнопкой;
- ** автоматический retry ** — система самостоятельно повторяет неудачный запрос по заданной стратегии.

В основном сценарии используется ** ручной retry в обоих подходах **, поэтому в React Query установлено:

```js
retry: 0;
```

Это позволяет сначала сравнить обработку одинаковой последовательности событий без дополнительного преимущества библиотеки.

При этом React Query имеет встроенную поддержку автоматических повторных попыток через параметр`retry`.Эта возможность рассматривается как дополнительное различие между подходами: в manual - реализации аналогичную стратегию необходимо программировать самостоятельно.

## Часть A / B — Error state и ручной retry

### Цель

Проверить, насколько способ управления server - state влияет на согласованность состояния интерфейса после ошибки запроса и при последующем retry.

### Manual

В manual - версии сначала демонстрируется типичная ошибка реализации.

После успешного запроса данные сохраняются в`state`.Если следующий запрос завершается ошибкой, но разработчик не очищает предыдущие данные, интерфейс может одновременно содержать:

- ошибку нового запроса;
- данные предыдущего успешного запроса.

Причиной является не HTTP - запрос как таковой, а вручную написанная логика управления несколькими взаимосвязанными состояниями.

В исправленной версии при переходе в `error` предыдущие данные явно очищаются:

```js
setData(null);
```

Таким образом, корректность результата достигается дополнительной логикой разработчика.

### React Query

React Query выполняет тот же пользовательский сценарий:

1. выполняется запрос;
2. запрос может завершиться ошибкой;
3. пользователь может выполнить`Retry`;
4. повторный запрос снова проходит через состояние загрузки и завершается новым результатом.

Вместо самостоятельного ведения:

```text
status
data
errorMsg
```

используются состояния запроса, предоставляемые библиотекой:

```text
isFetching
isError
isSuccess
data
error
```

Отдельная версия `BUG → FIX` для React Query не создаётся, поскольку исследуемая ручная ошибка возникает именно из - за самостоятельного управления переходами состояний.

### Проведение

1. Выполнить успешный запрос.
2. Включить симуляцию ошибки.
3. Выполнить следующий запрос и наблюдать состояние ошибки.
4. Выключить симуляцию ошибки.
5. Выполнить`Retry`.
6. Сравнить поведение Manual и React Query.

### Наблюдаемые параметры

Сравниваются:

- отображение`loading`;
- состояние после ошибки;
- наличие или отсутствие предыдущих данных;
- переход к повторному запросу;
- количество ручной логики, необходимой для поддержания согласованного состояния.

### Ожидаемый вывод

Оба подхода позволяют реализовать корректную обработку ошибки и повторного запроса.

Различие состоит в распределении ответственности: в manual - подходе согласованность`data`, `error` и статуса запроса обеспечивается написанным разработчиком кодом, тогда как React Query предоставляет готовую модель состояния асинхронного запроса.

Встроенный автоматический `retry` React Query в этой части намеренно не используется, поскольку сначала сравнивается одинаковый сценарий ручного повторного запроса.Его наличие фиксируется как дополнительная возможность библиотечного подхода.

## Часть C — Управление состоянием loading при ошибках и retry

### Цель

Цель этой части эксперимента — проверить, как выбранный способ управления server-state влияет на согласованность состояния `loading` при завершении запроса и при его повторном выполнении.

Для этого в manual-реализации намеренно моделируются две типичные ошибки разработчика, после чего те же события воспроизводятся средствами React Query.

### CASE 1 — «заблокированный loading»

#### Manual

При начале запроса вручную устанавливается:

```js
status = "loading";
```

Однако после завершения запроса состояние не переводится в `success` или `error`.

В результате запрос фактически уже завершён, но интерфейс продолжает отображать:

```text
Status: loading
Loading…
```

Таким образом, состояние UI перестаёт соответствовать реальному состоянию асинхронной операции.

#### React Query

В React Query используется тот же `fakeAPI` и аналогичный запрос.

Состояние выполнения запроса определяется через:

```js
isFetching;
```

Оно становится `true` во время запроса и изменяется после его завершения без необходимости вручную устанавливать следующий статус.

В результате аналог «заблокированного loading» при штатном использовании `useQuery` не возникает.

---

### CASE 2 — Retry без повторного loading

#### Manual

Первый запрос намеренно завершается ошибкой.

После этого выполняется успешный Retry, однако в ручной реализации перед повторным запросом намеренно отсутствует:

```js
setStatus("loading");
```

Поэтому запрос уже выполняется, но интерфейс не сообщает пользователю о повторной загрузке.

Это показывает, что при ручном управлении разработчик должен отдельно обеспечить корректный переход состояния при каждом новом запросе, включая retry.

#### React Query

В React Query используется один и тот же query:

```js
queryKey: ["exp2-errors-loading-2"];
```

Первый `refetch()` моделирует ошибку, а следующий `refetch()` — успешный повторный запрос.

Во время каждого выполнения запроса React Query автоматически устанавливает:

```js
isFetching === true;
```

Поэтому Retry также получает состояние загрузки без необходимости отдельно программировать его переход.

### Условия сравнения

Для Manual и React Query сохраняются одинаковые условия:

- используется один `fakeAPI`;
- используются одинаковые серверные данные;
- первый запрос в CASE 2 завершается ошибкой;
- повторный запрос завершается успешно;
- автоматический retry React Query отключён (`retry: 0`);
- запросы запускаются действиями пользователя.

Кнопка `Reset` используется только для возвращения демонстрационного сценария в исходное состояние и не является предметом сравнения.

### Проведение

**CASE 1**

1. Запустить запрос.
2. Дождаться его завершения.
3. Сравнить состояние интерфейса Manual и React Query.
4. Проверить, соответствует ли отображаемый `loading` фактическому выполнению запроса.

**CASE 2**

1. Нажать `Start z błędem`.
2. Дождаться состояния ошибки.
3. Нажать `Retry z OK`.
4. Наблюдать состояние интерфейса во время повторного запроса.
5. Сравнить Manual и React Query.

### Вывод по части Loading

Оба подхода позволяют реализовать корректную индикацию состояния загрузки, однако в manual-реализации её согласованность зависит от явных переходов состояний, написанных разработчиком.

Пропуск одной операции изменения `status` может привести как к постоянному отображению `loading` после завершения запроса, так и к отсутствию индикации во время реально выполняющегося Retry.

React Query связывает `isFetching` с жизненным циклом фактического запроса, поэтому разработчику не требуется вручную синхронизировать это состояние с каждым началом и завершением асинхронной операции.

# Общие выводы — Errors / retry

Эксперимент показал, что различие между manual-подходом и React Query проявляется не в возможности обработать ошибку как таковую: корректную обработку можно реализовать обоими способами.

Основное различие заключается в **распределении ответственности за состояние асинхронного запроса**.

В manual-реализации разработчик самостоятельно управляет:

- данными;
- ошибкой;
- состояниями `loading`, `error` и `success`;
- очисткой или сохранением предыдущих данных;
- переходом в `loading` при Retry;
- завершением состояния `loading`.

Эксперименты BUG/FIX показали, что пропуск отдельных переходов приводит к состояниям интерфейса, которые не соответствуют фактическому состоянию запроса.

React Query предоставляет состояния запроса (`isFetching`, `isError`, `isSuccess`, `data`, `error`) как часть собственного механизма управления server-state. Поэтому значительная часть логики переходов не реализуется разработчиком вручную.

При этом React Query не обязательно удаляет ранее полученные данные из кеша после ошибки повторного запроса. Состояние сохранённых данных и состояние текущей асинхронной операции управляются библиотекой отдельно, а способ их отображения определяется интерфейсом приложения.

В основном эксперименте автоматические повторные попытки React Query намеренно отключены:

```js
retry: 0;
```

Это позволяет сравнить одинаковое событие — ручной повторный запрос после ошибки — без изменения условий между подходами.

React Query дополнительно предоставляет встроенную возможность автоматического retry, тогда как в manual-подходе соответствующую стратегию повторных попыток необходимо реализовывать самостоятельно. Эта возможность рассматривается как дополнительное функциональное различие между подходами.

Таким образом, результаты этой части PB2 показывают, что специализированный механизм управления server-state уменьшает объём ручной логики, необходимой для согласования состояния интерфейса с жизненным циклом асинхронного запроса, и снижает вероятность ошибок, возникающих из-за пропущенных переходов состояний.
