# PB2 — Синхронизация: обоснование исследовательского вопроса

## 1. Почему синхронизация выделена в отдельный исследовательский вопрос

После получения данных с сервера возникает следующая задача управления `server-state`: состояние интерфейса должно оставаться согласованным с состоянием выполняющихся асинхронных операций.

Сам факт успешного выполнения HTTP-запроса ещё не гарантирует корректного состояния приложения. Между отправкой запроса и применением его результата проходит время, в течение которого могут произойти другие события:

- пользователь может инициировать следующий запрос;
- приложение может перейти в фоновое состояние и затем снова стать активным;
- запрос может завершиться ошибкой;
- после ошибки может быть выполнен повторный запрос;
- порядок завершения нескольких операций может отличаться от порядка их запуска.

Поэтому после базового вопроса о **получении server-state** возникает самостоятельная проблема его **синхронизации с жизненным циклом асинхронных операций**.

В рамках PB2 под синхронизацией понимается:

> **согласование актуального server-state и состояния интерфейса с текущим состоянием и результатами асинхронных запросов.**

Таким образом, синхронизация здесь не означает синхронизацию двух баз данных или постоянное выравнивание клиента и сервера. Термин используется в контексте клиентского React-приложения и описывает необходимость правильно определить:

- какой запрос в данный момент выполняется;
- какой его результат относится к актуальному состоянию приложения;
- когда необходимо инициировать обновление;
- как UI должен отражать выполняющийся запрос;
- как состояние должно измениться после успеха или ошибки;
- как должен обрабатываться повторный запрос.

Именно наличие этих взаимосвязанных асинхронных переходов отличает PB2 от базового получения данных, исследуемого в PB1.

---

# 2. Исследовательский вопрос PB2

Исследовательский вопрос можно сформулировать следующим образом:

> **Как ручное управление server-state и React Query различаются в обеспечении согласованности состояния приложения при асинхронных сетевых операциях?**

Для ответа недостаточно одного экспериментального сценария, поскольку нарушение синхронизации может возникать по разным причинам.

Поэтому вопрос разделён на три самостоятельных аспекта:

```text
                    СИНХРОНИЗАЦИЯ
                          │
          ┌───────────────┼───────────────┐
          │               │               │
        RACE          BACKGROUND       ERRORS /
      CONDITION      SYNCHRONIZATION     RETRY
          │               │               │
   Какой результат   Когда и как       Как состояние
   является          происходит        согласуется
   актуальным?       обновление?        с исходом
                                      запроса?
```

Все три части исследуют одну общую проблему — **согласованность server-state с асинхронным жизненным циклом приложения**, — но рассматривают различные источники возможного рассогласования.

---

# 3. Race condition — синхронизация результата с актуальным состоянием

Первая проблема возникает, когда несколько запросов существуют одновременно.

Асинхронность означает, что:

```text
Request A → запущен первым
Request B → запущен вторым

но:

Response B → получен первым
Response A → получен вторым
```

Последний полученный ответ не обязательно является ответом, соответствующим текущему состоянию приложения.

Следовательно, необходимо определить:

> **имеет ли полученный результат право изменить текущий server-state?**

Именно это исследует `Race condition`.

В Manual корректность требует дополнительного контроля актуальности результата.

В React Query исследуется механизм идентификации server-state через `queryKey` и связь результата запроса с соответствующим query.

Таким образом, Race представляет **синхронизацию по актуальности результата асинхронной операции**.

---

# 4. Background synchronization — синхронизация при изменении состояния приложения

Вторая проблема возникает не из-за конкуренции запросов, а из-за изменения состояния самого приложения.

Пользователь может:

```text
работать с приложением
        ↓
покинуть вкладку
        ↓
через некоторое время вернуться
```

В этот момент возникает необходимость определить поведение уже загруженного `server-state`.

В PB2 исследуется не вопрос его временной свежести — этот аспект отдельно рассматривается в PB3 — а механизм фонового обновления и состояние интерфейса во время выполняющейся операции.

Основные вопросы здесь:

- как обнаруживается возвращение пользователя;
- как инициируется фоновое обновление;
- как определяется, что запрос выполняется;
- как UI согласуется с жизненным циклом фонового запроса.

Таким образом, Background представляет **синхронизацию server-state с изменением активности приложения и выполняющимся фоновым обновлением**.

---

# 5. Errors / Retry — синхронизация состояния с исходом запроса

Третий источник рассогласования возникает, когда запрос не завершается успешно.

Асинхронная операция может пройти через последовательность:

```text
request
   ↓
loading
   ↓
error
   ↓
retry
   ↓
loading
   ↓
success
```

Каждый переход должен корректно отражаться в состоянии приложения.

При ручном управлении существуют несколько взаимосвязанных элементов:

- `data`;
- `loading`;
- `error`;
- `success`;
- состояние повторного запроса.

Если один из переходов пропущен, UI может перестать соответствовать фактическому состоянию операции.

Например:

```text
запрос завершён
↓
UI всё ещё показывает loading
```

или:

```text
Retry уже выполняется
↓
UI не показывает состояние загрузки
```

Поэтому Errors / Retry исследует:

> **как состояние приложения синхронизируется с изменяющимся исходом и жизненным циклом асинхронного запроса.**

Это третья самостоятельная сторона общей проблемы синхронизации.

---

# 6. Почему именно эти три аспекта объединены в PB2

Race, Background и Errors / Retry различаются по причине возникновения проблемы, но имеют одну общую структуру.

Во всех случаях существует:

```text
текущее состояние приложения
            +
асинхронная сетевая операция
            ↓
необходимость согласовать
новое состояние приложения
с произошедшим событием
```

Различается только событие, нарушающее простую последовательность `request → response`.

| Подэксперимент | Что нарушает простой сценарий                               | Что необходимо синхронизировать             |
| -------------- | ----------------------------------------------------------- | ------------------------------------------- |
| Race condition | несколько запросов завершаются в другом порядке             | результат запроса ↔ актуальное состояние    |
| Background     | приложение меняет активность и запускает фоновое обновление | UI/server-state ↔ фоновый запрос            |
| Errors / Retry | запрос завершается ошибкой и запускается повторно           | data/error/loading ↔ жизненный цикл запроса |

Поэтому эти три сценария логически относятся к одному исследовательскому вопросу.

Они позволяют исследовать синхронизацию не на одном частном примере, а в трёх принципиально разных ситуациях асинхронного поведения.

---

# 7. Почему эти аспекты не относятся к другим исследовательским вопросам

Выделение PB2 также необходимо для сохранения границ между исследовательскими вопросами всей работы.

## PB1 — Pobieranie

PB1 отвечает прежде всего на вопрос:

> **как выбранный подход влияет на организацию и количество запросов при получении одних и тех же server-state данных?**

PB2 начинается там, где одного факта получения данных уже недостаточно и появляется необходимость согласовывать состояние с асинхронными событиями.

---

## PB3 — Aktualność

PB3 исследует:

> **когда уже полученные данные следует считать актуальными и когда необходимо выполнить новый запрос?**

Это проблема freshness во времени.

PB2 / Background, напротив, исследует поведение **во время предусмотренного фонового обновления**.

Поэтому:

```text
PB2 → как согласуется состояние во время async update?

PB3 → нужен ли новый request с точки зрения freshness?
```

---

## PB4 — Mutacje

PB4 исследует изменение данных:

> **как после операции записи обеспечить согласованность отображаемого server-state с изменённым состоянием сервера?**

В PB2 серверные данные намеренно не изменяются как предмет эксперимента. Исследуется жизненный цикл операций чтения, ошибки, повторные запросы и асинхронная координация.

---

## PB5 — Parametry

PB5 рассматривает параметр как часть идентичности `server-state` и исследует изменение, последовательность и кэширование параметризованных данных.

В Race параметры используются только как средство создания нескольких конкурирующих асинхронных запросов.

Поэтому:

```text
Race → какой из конкурирующих результатов актуален?

PB5 → как параметр определяет идентичность server-state?
```

---

## PB6 — Koordynacja

PB6 переносит проблему на уровень нескольких потребителей одного `server-state`.

Исследуется:

> **как одно состояние разделяется и согласуется между несколькими компонентами и представлениями приложения?**

PB2, напротив, рассматривает согласованность состояния прежде всего относительно **жизненного цикла асинхронных запросов**.

---

# 8. Значение PB2 для общей структуры исследования

PB2 является естественным следующим этапом после базового получения данных.

Логика перехода выглядит следующим образом:

```text
PB1 — данные нужно получить
             ↓
PB2 — результат асинхронного получения
      нужно корректно согласовать
      с состоянием приложения
             ↓
PB3 — нужно определить,
      когда полученные данные
      перестают быть актуальными
```

Поэтому PB2 выполняет самостоятельную функцию в общей архитектуре исследования.

Он переводит сравнение Manual и React Query от простого вопроса **«как получить данные»** к более сложному вопросу **«как сохранить предсказуемое состояние приложения, когда сетевые операции развиваются асинхронно»**.

---

# 9. Обобщающий вывод

Выделение синхронизации в самостоятельный исследовательский вопрос обусловлено природой `server-state`.

В отличие от обычного локального состояния компонента, `server-state` зависит от внешних асинхронных операций, момент начала, длительность и результат которых не полностью определяются жизненным циклом React-компонента.

Поэтому приложение должно согласовывать собственное состояние с происходящими сетевыми событиями.

Три выбранных подэксперимента рассматривают эту проблему с разных сторон:

- **Race condition** — согласование с порядком и актуальностью результатов;
- **Background synchronization** — согласование с фоновым жизненным циклом обновления;
- **Errors / Retry** — согласование с результатом и состояниями выполнения запроса.

Такое разделение позволяет сравнить Manual и React Query не по наличию отдельных функций, а по тому, **каким образом каждый подход обеспечивает предсказуемое и согласованное состояние приложения в различных асинхронных ситуациях**.

Именно поэтому данные сценарии образуют единый самостоятельный исследовательский вопрос PB2 — **«Синхронизация»**.
